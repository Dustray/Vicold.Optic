### 修掉的关键缺陷（重要，后续别再踩）
1. **着色器 Y 轴翻转**：`gl_Position = p/uViewport*2-1` 把设计空间 y=0 投到屏幕**底部**，
   EGL 窗口坐标系原点在左下，而触摸坐标原点在左上 → 整个 UI 与预览上下颠倒。
   四个着色器统一改为 `1.0 - p.y/uViewport.y*2.0`。
2. **`text()` 顶点 stride 16 → 8**：vtx/uv 是两条独立紧密数组，逐顶点 2 float，16 会越界读。
3. 预览纹理在 `AImage_delete()` 之后仍被 `drawPreview` 使用 → 必须 `AHardwareBuffer_acquire()` 自持引用。
4. 字体图集行数原来按 16px/字形估，CJK（≈1em）会静默丢字 → 改按 `baked+2` 估并 +3 行。
5. 坐标变换只有 `offY_`，缺 `offX_`：cover 下横向溢出未居中，绘制与触摸命中不一致；
   且高度/尺寸误用 `screenY()`（混入偏移）→ 拆成 `dim()`（纯缩放）/ `screenX()` / `screenY()`。
6. 编译阻塞：缺 `EGL_EGLEXT_PROTOTYPES`、`GL_GLEXT_PROTOTYPES`、`STB_TRUETYPE_IMPLEMENTATION`；
   `glUniform4f` 传 3 参；`importPreviewImage`/`beginFrame` 未在头文件声明；`previewWindow() const` 与实现签名不一致。

## 修复：变焦拉到最广预览卡死（M1 采集稳定性）

用户报「焦距拉到最广时预览卡死」。真机复现 + 相机框架日志定位，根因有两点：

### 根因
1. **拖拽期高频 `setRepeating`**：`drainUiCmds` 原先在 `while(popCmd)` 循环里**每收到一个 UI 命令就调一次 `setRepeating`**（拖拽一帧积压多个 SET_ZOOM，≈10 次/秒）。本机 HyperOS/CamX HAL 对高频 `setRepeatingRequest` 敏感，会**静默掐断 repeating 预览流**——`setRepeatingRequest` 返回 OK 却不再交付 capture result（无 `onCaptureFailed` 回调），但单拍（captureOnce）仍可用。表现：预览冻结、frameCount_ 停摆。
2. **sub-1.0 超广角物理镜头缺陷**：机型 `zoom=[0.70,10.00]`，0.70 触发逻辑多摄切到超广角物理镜头（cameraID:6），该镜头 `CamX ERROR SENSOR SetCurrentflushOffset() m_ActuatorLibraryAPI.pSetCurrentflushOffset is NULL` 致动器库缺陷，预览流也会周期性断流。

### 修复（已编入，待真机复验）
- `core/capture/CameraDevice.cpp`：zoom 下限**保留原始值**（不再探测时抬到 1.0）；是否钳 1.0 由引擎 `uwAllowed_` 决定。
- `core/ui/Ui.h`：`kZoomMin=1.0f`，`kZoomStops={1,2,3,5,10}`（去掉 0.7 档）。
- `core/capture/CameraEngine.cpp`：
  - `drainUiCmds` 把 `setRepeating` 从「每命令一次」提到**每轮循环只发一次**（跨循环累计 `changed`）。
  - `onMove` 拖拽中**只更新 UI 显示不碰相机**，`onUp` 松手时**一次性下发**当前值（最多 1 次 setRepeating/手势，对本机 HAL 稳定）。
  - 新增**预览存活看门狗**：`onFrameResult` 打时间戳，run() 循环检测 >1.2s 无 result 则自动重发 `setRepeating`（通用安全网，处理任何瞬时断流）。
  - **超广角诊断开关**：`controls.txt` 加 `uw=1` 时 `uwAllowed_=true`，两处 zoom 钳制改为「开了 uw 才允许 sub-1.0」，默认仍钳 1.0（保流畅）。`pollControls` 解析 `uw` 并打 `ultrawide opt-in` 日志。

### 真机验证要点（已用）
- 屏幕常亮：`adb shell svc power stayon true`。
- 模拟拖拽：`adb shell input swipe` 用**物理屏坐标**（窗口 2506x1220，scale=1.694，off=(-136,0)，横屏左起 150px 挖孔被裁 → 窗口左缘在物理 x=150）。变焦滑块物理 x≈180..261、y≈234..979（设计 x98..146,y138..578）。

## 超广角是否可用：用户质疑 + 诊断准备

用户问「超广角用不了？」，质疑我直接禁掉 0.70。结论：**当前是"先保流畅禁掉"，但 0.70 在本机不可靠尚未定性**——
之前干净的单次 setRepeating 测 0.70 仍每 ~1.2s 掉一次，但无法区分是"镜头致动器硬件死穴"还是"超广角镜头流配置不对"。
用户选择 **重连后彻底查修**。已落地安全诊断通道（`uw=1` 开关，默认仍禁），打包完成待连设备跑决定性诊断。

### 决定性诊断结果（已连设备上，2026-09-29）
**结论：0.70 超广角在本机不可修复，是设备相机 HAL 配置缺陷，已确认保持禁用。**

1. 排除高频 setRepeating：改用合并重发+松手下发后，0.70 仍每 ~1.2s 掉（`preview stall` 12s 内 11 次，`frames=` 到不了 120）。
2. **顺带修了一个真实 bug**：`CaptureSettings.cpp` 把 `AE_MODE/AF_MODE/AWB_MODE` 当 `int32` 写（实际是 camera2 TYPE_BYTE），每帧报 `Camera2-Metadata: Mismatched tag type`。改成 `setEntry_u8` 后该错误归零（所有变焦档都受益，含 zoom=1.0）。但修了它 0.70 照样掉 → 与冻结无关。
3. **HAL 底层铁证**（logcat 落盘后精筛相机 HAL 进程 4459，时段 12:58）：
   - `CamX [HAL] LogRequest() ## REQUEST_ERROR ## RESULT_ERROR ## BUFFER_ERROR`
   - `camxncsintfqsee.cpp GetConfig() QSEE connection is not running, sensorType=35/33/38`
   - `camxncsintfois.cpp FillCap() No Provider Object with cameraId: 2 available` / `RequestNCSService() Failed to query capabilities, result=CamxResultENoSuch`
   - `camximagesensordata.cpp GetSensorModeValidationTable() without SensorModeValidationTable`（反复）
   - `camxapois.cpp ReleaseLensPositionReadResources() [APOISReadHallGyroData] m_pReadHallGyroData = NULL`
   - cameraId 0=wide(sensorRole0)、3=tele(sensorRole3)、2=超广角；超广角走的安全/NCS 子系统（QSEE）未起、sensor mode 校验表缺失、OIS 读数句柄 NULL。
4. **判定**：超广角（cameraId=2）在本机的相机 HAL 配置本身是坏的（缺 SensorModeValidationTable、NCS provider 不可用、QSEE 未连、OIS 句柄 NULL）→ 这是**设备/固件 HAL 缺陷，应用层改流配置/元数据都无法修复**。stock 相机可能走不同 sensor mode 或绕开 NCS 安全路径才"能用"。
5. **默认（无 uw / zoom=1.0）验证**：Mismatched=0、stall=0、frames 120→240(6s) 流畅 30.1fps、raw 30.6fps → 主摄原生广角路径完全健康。

### 最终处置
- `CameraDevice.cpp`：zoom 下限保留原始值（不再探测时抬 1.0），由引擎 `uwAllowed_` 决定；**默认仍钳 1.0**（保流畅），`uw=1` 开关作为高级用户自担风险入口。
- `CaptureSettings.cpp`：AE/AF/AWB mode 改用 `setEntry_u8`（真实修复，已验证）。
- `uw=1` 仍保留（看门狗兜底不永久卡死），但普通用户不应开启 0.70。
- 不再尝试"显式切物理镜头/改预览尺寸"等方案：HAL 在 sensor 驱动层就缺配置，应用层无解。

## 超广角修复：物理直连方案落地（真机验证通过）

### 根因链（三步定位）
1. 排除法：`raw_mode=once`（RAW 移出 repeating）后 0.70 依然 11 断流/12s → RAW 假设排除；
   1920×1080 预览同样断流 → 预览尺寸排除。
2. `cam=2` 直开失败：超广角物理 ID **不在** getCameraIdList 里，无法独立打开，必须经逻辑摄 0。
3. 结论：`ZOOM_RATIO<1.0` 走逻辑多摄融合管线（CamX deblur/SAT/GME + QSEE + SensorModeValidationTable
   缺失）才是断流根因。其他 app 之所以能用超广角，是走物理摄像头直连，绕过融合。

### 关键事实修正
- **超广角是物理 ID 3（焦距 2.57mm），不是之前假设的 2**。自动探测逻辑（物理成员中
  AVAILABLE_FOCAL_LENGTHS 最短者）结果可靠；diag_cam.txt 为证据。
- 超广角物理镜头不支持 RAW（会话输出仅预览 1 条）。

### 实现要点
- `CaptureSession::create(dev, outputs, physicalId)`：physicalId 非空时预览输出用
  `ACaptureSessionPhysicalOutput_create`，repeating 用 `ACameraDevice_createCaptureRequest_withPhysicalIds`。
- `CaptureSettings::apply(req, skipZoom)`：物理直连时不写 ZOOM_RATIO（写 <1.0 会再次触发融合）。
- `CameraEngine`：会话签名 `L+R` / `P:3`，`commitSession()` 检测签名变化决定重建或仅重发；
  RAW 拍摄（triggerBurst/shot_raw）在超广角下拒绝并 toast。
- controls.txt 新键：`uw=1`（默认开）、`uw_phys=N`（强制物理 ID，诊断用）。

### 修掉的真 bug
1. **冷启动误入超广角**：`uwActive()` 把默认 zoomRatio=0.00 当 <1.0 → 加 `zoom>0` 条件。
2. **会话重建 UAF（SIGABRT）**：tombstone `C2N-dev-looper` 线程
   "pthread_mutex_lock called on a destroyed mutex" —— 旧 CaptureSession 立即析构，
   但框架回调线程还持有 capCbs_/mutex_。修法 = 退役墓地：旧会话立即 close、延迟 1.5s 析构
   （`retired_` + `reapRetired()`，run 循环每轮回收）。
   注意：当时 logcat 里"回切 L+R"日志出现在崩溃信号之后，是崩溃伴生症状，非独立逻辑 bug。

### 真机验证（13:39 运行段）
- L+R 基线 → `P:3` 切换 → 43s 超广角稳定运行：**0 断流、0 HAL 错误**（修复前每 1.2s 一波错误风暴）、
  29.9fps；切回 `L+R` 后 RAW 恢复 30.9fps；HAL 错误仅出现在两次会话重建瞬间（各 ~7 条，良性瞬态）。
- 截图对比 `uw_on.png`（超广角）/`uw_shot.png`（主摄）：FOV 差异明显，超广角真实出图。

- UI 变焦导轨仍是 kZoomMin=1.0（kZoomStops 无 0.7），超广角目前仅 controls.txt 可达；

## UI 变焦导轨：0.7 档 + 松手回弹 bug 修复（真机验证通过）

### 松手回弹根因（用户报告"大于1.0的松手瞬间预览回到1.0，导轨不动"）
- `pollControls()` 每轮新建**局部** ControlFile → 内容比对状态（lastKv_/hasLast_）被重置 →
  controls.txt 每 100ms 全量重放。设备文件里残留测试期写入的 `zoom=1.0`，UI 刚设的 zoom
  下一轮就被盖回；导轨显示是 UI 自身状态所以不动。这正是审查记录的 P1"ctl_ 死成员"缺陷的实际危害。
- 修法：ControlFile 改为引擎成员 `ctl_`（unique_ptr，run() 里按 dataDir 创建），重放仅在文件内容真变时发生。

### 导轨 0.7
- `Ui.h`：kZoomMin=0.7f，kZoomStops={0.7,1,2,3,5,10}，zoom_ 初始 1.4→1.0（原值与引擎不符）。
- 0.7–1.0 区间为超广角原生 FOV（物理直连不写 ZOOM_RATIO，段内无数字变焦，预览在该段不随导轨变化）。

### 真机验证（13:55 运行段，adb input swipe 模拟导轨触摸）
- 导轨命中点换算：cover 映射 scale=1.7026，offY=-2.9；2.0 档=(208,678)、1.0 档=(208,856)、0.7 底=(208,947)。

## 大变焦卡死修复：物理直连推广为通用分带机制（真机验证通过）

### 现象与定位（用户报告"多拖动几次会卡死，不局限于超广角"）
- 变焦阶梯探测：2.0/3.0 干净，**5.0/10.0 持续断流**（每 ~1.2s，与超广角同 signature）；
  看门狗 12 次重试耗尽后预览永久黑屏 = 用户感知的"卡死"。
- dump 焦距：物理成员 3=2.57mm(超广) / 2=6.62mm(主) / 4=17.42mm(长焦，f 比 = **2.63x**)。
- 结论：逻辑融合管线第二个坏区 = 高倍数字变焦（SAT/长焦融合），与 sub-1.0 同族。
  修复 = 把物理直连从超广角特例推广为按 zoom 自动分带。

### 实现
- `CameraDevice`：通用物理布局探测（成员焦距最短=uw / 居中=main / 最长=tele），
  traits 新增 telePhysicalId / teleNativeZoom(=f_tele/f_main=2.63) / mainFocal。
- `CameraEngine::activePhysId()`：z∈[0.7,1.0)→P:uw；z≥teleMinZoom_(默认=teleNativeZoom，
  恰在 SAT 坏区前切)→P:tele；其余→逻辑。`physZoom()`：长焦直连写相对数字变焦 z/2.63。
- `CaptureSession::setRepeating(targets, s, physZoom)`：物理直连时写 physZoom 而非用户 zoomRatio。
- controls 新键：`tele_phys=N`、`phys_min=N`（诊断强制）。
- 看门狗重试耗尽（12 次）→ closeSession 全链路重连，不再永久黑屏。
- 物理直连模式下 RAW 拍摄守卫改为"任意直连模式拒绝"（uw/tele 均无 RAW 流）。

### 真机验证（14:16-14:18 运行段）
- 全段阶梯：2.0→L+R、3.0→P:4(1.14x)、5.0→P:4(1.90x)、10.0→P:4(3.80x)、0.7→P:3 —— **全部 0 断流**
  （5.0/10.0 修复前分别为 5 次/持续死锁）。
- 压力：10 次快速跨带拖动（12 次会话切换）→ 0 断流 0 崩溃，fps 29.3，RAW 持续。
- 注意：物理直连下 result 的 zoomRatio 报相对值（3.80@10x），非用户倍率 —— stats/HUD 显示如此，属预期。

## 拖动实时变焦（真机验证通过）

### 需求与旧设计
- 用户报告：变焦"只有抬手之后才生效而且有延迟"。旧设计 onMove 只更新 UI 显示、
  onUp 才下发 —— 这是当初误诊"高频 setRepeating → 断流"时留的规避。断流真因是
  融合管线坏区，已由分带物理直连绕开，实时下发可以恢复。

### 实现
- `Ui::pushZoomLive()`：onMove 中节流 ≥120ms 实时入队 SET_ZOOM；onUp 无条件补发终值。
- `Ui::zoomFromY(y)`：onMove/onUp 共用的导轨换算（对数+吸附）。onUp 用**松手位置**
  重算终值 —— 快速甩动时输入管线丢弃末尾 MOVE，只信最后一次 MOVE 终值会偏
  （实测 150ms 甩动停在 8.76 而非 10.0，修复后精确 10.00/0.70）。
- 引擎循环拾取节拍 100ms→50ms（拖拽命令最坏延迟 120+50ms，平均 ~95ms）。
- 引擎侧不变：drainUiCmds 每轮合并所有积压命令 → 单次 commitSession（≤8 setRepeating/s）。

### 真机验证（14:31-14:40 运行段）
- 慢拖 1.0→5.0（900ms）：6 个中间值依次生效（1.15…5.00），跨 2.63 一次会话重建，0 断流。
- 带内拖 1.0→2.4：7 个中间值实时生效，0 会话重建、0 断流。
- 快速甩动 150ms：1.0→10.00 / 10.0→0.70 精确落位（P:4→P:3 直切），0 断流。
- 拖动期间 28-29.7fps，RAW 环 30.7fps 持续。
- 教训：adb 测试前先确认屏幕亮且退出防误触模式（KEYCODE_VOLUME_UP 可退出）。

## 拖动卡顿修复：GL 裁切平滑变焦 + 带间滞回（真机验证通过）

### 量化定位（帧节奏探针：result 间隔 >70ms 计断裂）
- 静置 6s：0 gaps（max 43ms）；带内拖动（~8 次/s 实时重发）：**0 gaps**（max 47ms）；
  跨带拖动：+2 gaps，**max 285ms**。
- 结论：卡顿全部来自跨带会话重建（~285ms 冻结），带内重发零丢帧。

### 实现
- GL 数字裁切平滑变焦：Gl::setPreviewZoom（uCrop 同域等比缩小取样窗）。
  拖拽上拉越带时相机侧钳在 teleMin−0.08 实时跟随（带内零重建），
  越带部分 crop = zoom_/appliedZoom 由 GL 每帧补齐；引擎按 result 回传
  appliedZoom（物理带按带基换算回用户域），收敛后 crop 恒回 1 无跳变；
  松手才推真实值触发重建（冻结只在落位瞬间）。
- 超广角带连续变焦：physZoom() 扩展 uw 相对变焦 rel = z/0.7，0.7–1.0 段真实跟手
  （此前恒原生 FOV）。
- 带间滞回（引擎 physBand_）：uw 退出 z≥1.03、tele 退出 z≥teleMin−0.08，
  防边界微动重建风暴（实测 0.86↔1.00 摆动 3 次重建 → 0）。
- 下拉越带（tele→main、main→uw）裁切无法模拟变宽，重建仍在途中（每次 ~300ms）；
  彻底消除需多读出流常驻会话（GL 切纹理源），列为后续优化。

## 拖动闪烁修复：变焦双模式（放大冻结 / 缩小跟随）（真机验证通过）

### 闪烁根因
- appliedZoom（帧元数据）先于 GL 纹理像素数帧到达（acquire 队列滞后）。
  旧实现相机 8Hz 阶梯跟随 + crop=zoom_/az 反向补偿，二者同时活跃 ——
  每次 az 跳变时纹理还是旧画面，FOV 来回错位 = 闪烁。点按档位同理
  （crop 立即修正 → 相机生效 → crop 突回 1，中间帧冲高）。

### 修法（双模式 + 归一，core/ui/Ui.{h,cpp}）
- 放大方向（zoom_ ≥ az）：相机冻结不发命令，crop = zoom_/az —— 纹理不变、
  crop 单调连续，FOV 精确 = zoom_，零错位零延迟；crop 上限 4→16
  （uw 0.7 拖到 10x 时 crop≈14.3，暂态数字裁切糊但可用）。
- 缩小方向（zoom_ < az）：crop 恒 1，相机节流实时跟随（带内 0 丢帧）。
  GL 无法扩 FOV，这是物理边界；跨带重建仍在途中（单流约束）。
- az 真实变化时 cropSmooth 立即归一 1（元数据与像素同帧绑定，切换是单次
  跳变；若让 crop 从高位平滑下降会与纹理过渡叠加冲高 —— 实测闪烁来源之二）。
- cropSmooth 指数平滑（20/s，帧率无关）兜底残余微差。
- 删除 onMove 的 teleMin 钳制逻辑（冻结方案下不再需要）。
