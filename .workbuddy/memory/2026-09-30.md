## 用户上手反馈的三症状 → 三项修复（commit 6f813b7，真机验证通过）

用户反馈（触摸路径）：① 长焦丝滑但从很长处才开始变 ② 主摄到长焦缺失一段
③ 主摄变焦不丝滑卡顿 ④ 超广↔主摄切换有一段焦距重叠。

### 根因（三个，同源：FOV 换算基准 + 补偿机制）
1. **超广基准用错**：uw 带 crop 基准硬编码 0.7（导轨下限）而非光学倍率
   f(uw)/f(main) = 2.57/6.62 = 0.388。显示 FOV = 0.388×z/0.7 ≈ 0.55z ≠ z
   → 与主摄带 1.0 处接不上 = 重叠/跳变。修：traits.uwNativeZoom（探测时算
   fMin/fMain），az 回传与 physZoom 全部改用它。
2. **逻辑流提前钳住**：effSettings zmax = min(2.5, teleMin−0.05) = 2.50，而
   长焦接管点 2.63 → 2.50~2.63 逻辑流停变而长焦未接管 = 缺失一段。
   修：zmax = teleMinZoom_（切换点即上界，逻辑带显示上限本就是 2.63）。
3. **主摄带没有 crop 补偿**：crop 只在物理带生效，主摄带 crop 恒 1 → 画面
   完全靠相机 120ms 节流跟随 = 8 次/s 阶梯跳 = 卡顿。修：crop = zoom_/az
   全带统一，相机跳一步 crop 同步收，每帧连续。

### 关键实现细节（易错）
- **az 变化时 crop 必须落位到新 target，不能归一到 1**。归一 → FOV 退回 az
  再爬升，与纹理过渡叠加 = 泵动闪烁（2026-09-29 全程闪烁的元凶）。
  落位 → FOV 立即 = zoom_，无爬升过程。静止时 az=zoom_ → crop=1（不裁切）。
- lastAz_ 成员曾被误删（废除 crop 机制时），重新加回。

### 真机数据
- uw 带 z=0.9：az=0.39 crop=2.318 → FOV = 0.388×2.318 = 0.90 = z ✅ 与主摄带连续
- 主摄带 z=2.60：stats eff zoom=2.60（原 2.50 死区消失）、crop dbg
  slot=0 az=2.60 crop=1.000（稳态不裁切）✅

### 经验
- 光学倍率 vs UI 量程是两个量：导轨下限（0.7）不能当 FOV 换算基准。
- 「丝滑」= 每帧连续补偿，不是相机跟随频率；相机节流下必须靠 GL crop 补差。

## 用户上手反馈「2.6x 就切长焦」→ 根因是倍率算错（commit 64f2aa3）

用户给的 MIUI 口径：0.7x=17mm、1x=23mm、5x=115mm，切换点在 1x 与 5x。
对照后发现 **倍率一直用焦距比，漏了传感器尺寸**：

| 摄 | f | sensorW | 等效 | 焦距比(错) | 等效比(真) |
|---|---|---|---|---|---|
| uw 3 | 2.57 | 5.014 | 18.5mm | 0.388 | **0.774** |
| main 2 | 6.62 | 9.994 | 23.8mm | 1.0 | 1.0 |
| tele 4 | 17.42 | 5.243 | 119.6mm | 2.63 | **5.016** |

分带与 GL crop 全建立在这两个错值上 → 三项 FOV 症状 + 2.6x 提前切长焦。
修：`zoomOf = (f/w)/(f0/w0)`（CameraDevice 探测，缺 w 时回退焦距比）。

### 长焦接管点必须落在逻辑流安全区内
- 实测（每点静置 6s 数 `preview stall`）：**4.6/4.8 = 0 stall，5.0 起 = 6 次/6s**，
  且逻辑流 zoom 被 HAL 硬钳在 5.00（请求 5.2 时 az 仍 5.00）。
- 按原生 5.016 接管 → 用户拖到 5x 时逻辑流已在断流：画面先冻结、再随长焦接管跳变
  = 用户所说「5x 瞬间放大好多」。
- 修：`teleSwitch_ = min(teleNative, 4.85)`；effSettings 逻辑流钳制上界同步用它。
  代价：4.85–5.02 约 3.5% 小死区（crop 不能 <1）。
- 10x 现在只需 1.99 倍数字裁切（此前 3.80）。

### 验证与工具（新增 tools/）
- `zoom_scan.sh`：逐点设 zoom 读 crop dbg，核对 eff FOV = az×crop 是否 == z。
  修复后 0.78→10.0 全程偏差 <0.006，跨 1x/5x 连续，0 stall。
- `stall_probe.sh`：逐点数 stall，定位断流区间（比"看帧数增长"可靠 —— 帧数会因
  看门狗重发而虚增，曾据此误判 4.9/5.5 都 OK）。
- `logical_limit.sh` / `calib_fov.py`（后者在本场景不可靠，见下）。

### 坑（记录防重蹈）
- **截图必须指定主屏**：pandora 有副屏，`screencap` 默认抓到副屏（桌面），
  要用 `-d 4630946949513469331`（`dumpsys SurfaceFlinger --display-id` 取）。
- **Git Bash 下 adb 路径**：`$ROOT/build/x`（/d/...）原生 adb 不认，`/sdcard/...`
  会被转成 Windows 路径 → 脚本内 `cd $ROOT` 用相对路径 + `MSYS_NO_PATHCONV=1`。
- **像素标定不可靠**：近景（桌面 ~50cm）三摄基线视差在 5x 下占画面 20%+，
  加畸变/曝光差 → NCC 峰值淹没；已知 2x↔4x 对照都测错（k=0.065）。需远景(>3m)才可用。
- **系统相机抢占**：用户切到 com.android.camera 时我们的 app 会被挤掉，
  表现为 preview stall 风暴 + 进程消失 —— 不是回归，先 `topResumedActivity` 确认。
- disp 诊断键两版坑：原本每轮被 commitSession 盖回（失效）；改成"仅变化时写"后
  又变成手动值永久卡住。最终 `manualDisp_` 标志：手动期间保持，分带变化才交还自动。
