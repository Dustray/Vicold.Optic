## 用户上手反馈的三症状 → 三项修复（commit 6f813b7，真机验证通过）

用户反馈（触摸路径）：① 长焦丝滑但从很长处才开始变 ② 主摄到长焦缺失一段
③ 主摄变焦不丝滑卡顿 ④ 超广↔主摄切换有一段焦距重叠。

### 根因（三个，同源：FOV 换算基准 + 补偿机制）
1. **超广基准用错**：uw 带 crop 基准硬编码 0.7（导轨下限）而非光学倍率
   f(uw)/f(main) = 2.57/6.62 = 0.388。显示 FOV = 0.388×z/0.7 ≈ 0.55z ≠ z
   → 与主摄带 1.0 处接不上 = 重叠/跳变。修：traits.uwNativeZoom（探测时算
   fMin/fMain），az 回传与 physZoom 全部改用它。
2. **逻辑流提前钳住**：effSettings zmax = min(2.5, teleMin−0.05) = 2.50，而
   长焦接管点 2.63 → 2.50~2.63 逻辑流停变而长焦未接管 = 缺失一段。
   修：zmax = teleMinZoom_（切换点即上界，逻辑带显示上限本就是 2.63）。
3. **主摄带没有 crop 补偿**：crop 只在物理带生效，主摄带 crop 恒 1 → 画面
   完全靠相机 120ms 节流跟随 = 8 次/s 阶梯跳 = 卡顿。修：crop = zoom_/az
   全带统一，相机跳一步 crop 同步收，每帧连续。

### 关键实现细节（易错）
- **az 变化时 crop 必须落位到新 target，不能归一到 1**。归一 → FOV 退回 az
  再爬升，与纹理过渡叠加 = 泵动闪烁（2026-09-29 全程闪烁的元凶）。
  落位 → FOV 立即 = zoom_，无爬升过程。静止时 az=zoom_ → crop=1（不裁切）。
- lastAz_ 成员曾被误删（废除 crop 机制时），重新加回。

### 真机数据
- uw 带 z=0.9：az=0.39 crop=2.318 → FOV = 0.388×2.318 = 0.90 = z ✅ 与主摄带连续
- 主摄带 z=2.60：stats eff zoom=2.60（原 2.50 死区消失）、crop dbg
  slot=0 az=2.60 crop=1.000（稳态不裁切）✅

### 经验
- 光学倍率 vs UI 量程是两个量：导轨下限（0.7）不能当 FOV 换算基准。
- 「丝滑」= 每帧连续补偿，不是相机跟随频率；相机节流下必须靠 GL crop 补差。

## 用户上手反馈「2.6x 就切长焦」→ 根因是倍率算错（commit 64f2aa3）

用户给的 MIUI 口径：0.7x=17mm、1x=23mm、5x=115mm，切换点在 1x 与 5x。
对照后发现 **倍率一直用焦距比，漏了传感器尺寸**：

| 摄 | f | sensorW | 等效 | 焦距比(错) | 等效比(真) |
|---|---|---|---|---|---|
| uw 3 | 2.57 | 5.014 | 18.5mm | 0.388 | **0.774** |
| main 2 | 6.62 | 9.994 | 23.8mm | 1.0 | 1.0 |
| tele 4 | 17.42 | 5.243 | 119.6mm | 2.63 | **5.016** |

分带与 GL crop 全建立在这两个错值上 → 三项 FOV 症状 + 2.6x 提前切长焦。
修：`zoomOf = (f/w)/(f0/w0)`（CameraDevice 探测，缺 w 时回退焦距比）。

### 长焦接管点必须落在逻辑流安全区内
- 实测（每点静置 6s 数 `preview stall`）：**4.6/4.8 = 0 stall，5.0 起 = 6 次/6s**，
  且逻辑流 zoom 被 HAL 硬钳在 5.00（请求 5.2 时 az 仍 5.00）。
- 按原生 5.016 接管 → 用户拖到 5x 时逻辑流已在断流：画面先冻结、再随长焦接管跳变
  = 用户所说「5x 瞬间放大好多」。
- 修：`teleSwitch_ = min(teleNative, 4.85)`；effSettings 逻辑流钳制上界同步用它。
  代价：4.85–5.02 约 3.5% 小死区（crop 不能 <1）。
- 10x 现在只需 1.99 倍数字裁切（此前 3.80）。

## NDK 多摄结果交付模型纠正 + 主摄带 az[0] 修复（下午，编译通过）
- **关键事实**：NDK camera2 的 `onCaptureCompleted` 每个 repeating 帧**只回调一次**，
  交付的是**逻辑融合结果**（单条 `ACameraMetadata*`）。不存在"每路物理输出各回调一次"
  的模型。per-physical 结果需走 `logicalCamera` 回调变体（带 physicalResultCount/
  physicalCameraIds/physicalResults），或用 `ACameraMetadata_getPhysicalCameraMetadata`
  从逻辑结果里抽取。此前"三路结果各回调"的假设是错的。
- 逻辑结果携带 `ACAMERA_LOGICAL_MULTI_CAMERA_ACTIVE_PHYSICAL_ID`（byte，START+2），
  标识当前主源物理摄像头（"2"主/"3"超广/"4"长焦）——**诊断用**，不是"哪路输出"标识。
  **单数 `ACAMERA_LOGICAL_MULTI_CAMERA_PHYSICAL_ID` 在 NDK 中不存在，会编译失败**；
  复数 `PHYSICAL_IDS` 是 characteristics 用的。已修正 CaptureSession.cpp。
- **主摄带卡顿根因（最终版）**：此前 `onFrameResult` 用 `if (r.physicalId.empty())`
  判定"逻辑流"才更新 az[0]。一旦把标签修正为 ACTIVE_PHYSICAL_ID，逻辑结果恒带非空
  physicalId → 该分支**永不触发** → az[0] 卡在 1.0 → crop=zoom_/1.0=zoom_ 作用在已是
  zoom_ 倍率的纹理上 → 预览被放大到 zoom_² 倍（主摄带彻底失真）。
- **修法**：az[0] 直接由逻辑结果 ZOOM_RATIO 每帧驱动（`ui_->setAppliedZoom(0, r.zoomRatio)`，
  去掉 physicalId 判定）。NDK 单帧单结果，其 ZOOM_RATIO 即逻辑流实际出图倍率（=effSettings
  的 clamp 值），与 UI 节流目标 zoom_ 之差由 GL crop 补，FOV 连续。az[1]/az[2] 仍用恒定
  带基（幂等）。帧率探针/近距判定也去掉 physicalId.empty() 门槛（单帧单结果，无需区分）。
- 编译经 cmake --preset android-arm64 + ninja 通过（0 warning）。**真机验证（pandora 接入后跑通）**：
  - `tools/zoom_smooth_probe.sh 1.0 5.0 0.1 0.12`：拖动 1.0↔5.0 段 `pacing: gaps=0 max=68ms` → 0 掉帧。
  - 逐帧 `crop dbg` 抓 1.0→3.0 过渡：zoom 瞬跳 3.0 后 az 仍 1.0 约 7 帧(228ms)，期间 cropSmooth_
    指数爬升 1.0→2.98（数字补偿 120ms 光学滞后），第 8 帧 az 追上 3.0 → crop 落位 1.000 稳定。
    FOV=az×crop 过渡期(1×爬升1→3)与交接(3×1.0)连续无 pop —— **与长焦带丝滑机制一致，主摄带卡顿修复确认**。
  - 旧 bug 是 az 永久卡 1.0 → crop 常驻 3.0 → 9x 过放大；新行为 az 跟上、crop 回落 1.0，已消除。

## 探针环境坑（本机 Git Bash/MSYS 跑通，2026-09-30）
- **`zoom_smooth_probe.sh` 原 setzoom 用 `$ROOT/build/ctl.txt`（`/d/...` MSYS 路径）**，本机
  `adb.exe` 解析不了 → push 失败、zoom 从不被驱动。已加 `LOCAL_CTL=$(cygpath -w "$ROOT/build/ctl.txt"

  会被转成 `C:/Users/.../storage/...` 导致 push 失败。

## 主摄带"两焦距间来回闪"真正根因 + crop 平滑修复（傍晚，pandora 真机确认）
- **用户最终明确的症状**：1–5x 拖拽时预览在"当前手指焦距"和"另一个焦距"之间来回闪
  （≠掉帧——`pacing: gaps=0 max=60ms` 全程不掉帧）。静止在某焦距时 `az` 稳定=crop 稳定=1.000，
  说明 az 锚点无 bug；问题**只在拖拽（连续变焦）过程**。
- **真正根因**：`Ui.cpp` 同带内变焦的 `azChanged` 分支让 `cropSmooth_ = target` **瞬时落位**。
  pandora 光学变焦是**离散台阶式**生效（ZOOM_RATIO 每档跳，az 2.0 停几帧→2.5 停几帧），az 每跳一档
  crop 就一帧到位跟着跳 → 预览跟着相机台阶"跳焦距" = 用户所见"两焦距间闪"。
  （此前下午那版把根因误判为 az 锚点被污染；az[0] 由逻辑 ZOOM_RATIO 每帧驱动本身没错，
  但那个修复没解决"闪"——闪源于 crop 的瞬时落位，而非 az 值。）
- **为何长焦带(5–120x)丝滑**：`az` 恒为带基常量，`crop=zoom_/teleNative` 纯由手指 `zoom_` 驱动且
  平滑，完全绕开相机离散变焦（物理流恒原生 FOV，pandora quirk）。主摄带却依赖相机光学变焦 → 必吃台阶。
- **修法**：`Ui.cpp` 同带内变焦改为**始终指数平滑**（仅 `slotChanged` 跨带才瞬时落位，防两摄像头画面
  交叉淡化混叠）；删 `azChanged` 瞬时落位分支。`cropSmooth_ += (target-cropSmooth_)*(1-exp(-dt*20))`
  把相机离散台阶抹成连续变焦，与长焦带机制一致。
- **crop 下限 1.0 保留（物理约束）**：下降段 `az>zoom_` 时 `target<1` 被钳 1.0（GL 不支持 crop<1：
  相机纹理是 az 倍 FOV 无更宽数据，缩小会采样越界）。平滑后下降段表现为"缓回满幅"而非"瞬时节流卡死"。
  彻底零画质损失的方案需相机出图预留 margin（SCALER_CROP_REGION 取<满幅），暂未做。
- **验证（pandora 真机，剧烈来回拖 1.0↔5.0 @60ms 大幅反转）**：`crop` 相邻帧变化 ~0.06 连续平滑
  （1.118→1.182→1.216…），无瞬时节流跳变；相机台阶被 crop 平滑滤波抹平。静止 `crop=1.000` 不变。
- `crop dbg` 诊断频率已调为每 30 帧(≈1s)一条，便于用户真机手指拖拽时自测。

## 晚：跨带切换闪帧根治（物理流继承模型 + 原生 FOV 翻转门）

**症状**：近距 20x 处切长焦瞬间闪一帧「未偏移位置」画面再固定到正确位置。
**根因**：pandora quirk 之二（物理流继承逻辑 ZOOM_RATIO 裁切）—— 主摄带逻辑写 4.85
时，长焦纹理实际 FOV = 5.016×4.85 ≈ 24.3x；切换瞬间显示的第一批长焦帧还是
切前捕获的继承裁切帧，用常量 az=5.016 配 crop → 错位闪帧，等逻辑 zoom=1.0 的
原生帧到达（~190ms）才固定。昨日时间戳对齐只做了 slot 0，物理 slot 1/2 仍是常量。

**修法（两层）**：
1. **azForSlot 扩展继承模型**：az_物理(t) = 带基 × logicalZoomAt(t)（slot1 带基
   uwNativeZoom_、slot2 teleMinZoom_，逻辑 zoom 按帧时间戳查同一结果环）。
   继承裁切纹理的 crop 从此严格同源。tele 带逻辑恒 1.0 → 恒 5.016，稳态不变。
2. **翻转加「原生 FOV 就绪」门**（Ui::frame 切显示源处）：目标 slot 的匹配 az
   ≤ 带基×1.5+0.05 才翻转 + 交叉淡化；未就绪时旧 slot 继续 GL 补偿（crop 上界
   32 覆盖近距 20x）。等待期 = 逻辑 1.0 经 120ms 节流落地 + 管线延迟 ≈ 200ms。
   翻转时打 `preview slot A -> B (az=.. base=..)` 日志。

**真机验证**（近距扫 1→20→1）：上行 `0 -> 2 (az=5.02 base=5.02)`、下行
`2 -> 0 (az=1.00 base=1.00)`，az×crop≡zoom 全程自洽，零崩溃。

## 晚 7：直方图功能完善（GL 降采样统计 + 绘制增强）

**根因**：直方图此前恒空 —— 预览流是 AIMAGE_FORMAT_PRIVATE（小米 HAL 劫持 YUV/RGBA
ImageReader 通路，见 makePreviewSource 注释），AImage_getPlaneData 仅支持
YUV_420_888 → CPU 直读是死路，唯一路径是 GL 采样。

**实现（Gl 层）**：
* 降采样管线：预览纹理（EXTERNAL_OES）→ 128×96 RGBA FBO（LINEAR）→ glReadPixels
  → CPU 统计 64-bin RGB。新增 kVsHist/kFsHist（samplerExternalOES）、ensureHistRt
  （lazy 建 FBO/program，detach 全清理）、sampleHistogram、copyHistogram。
* **节流 120ms**（readPixels 同步 stall 管线）+ **只统计显示源**：acquirePreview 签名
  改为 (slot, wantHist)，Ui 传 `s == histSlot`（previewActive_，翻转等待期跟随旧显示
  源）。统计放在 AImage_delete 之后（读回期间不占 maxImages 配额）。
* 读回后恢复 FBO binding + viewport（beginFrame 每帧设 viewport 兜底）。
* 静态 readPixels 缓冲 48KB（渲染线程独占）。

**绘制增强（Ui::drawHistogram）**：
* 通道颜色修正：旧版 R→蓝/B→橙错色，改 R 红 / G 绿 / B 蓝，三通道同位 alpha 叠加；
* 3-bin 平滑（1:2:1）抹单 bin 噪声；
* **gamma 0.6 归一化**：线性 max 下单色场景尖峰会把其余 bins 压贴地；
* **两端裁切警示**：端点 bin 占比 >1.5%（任一通道）→ 框内边缘红色窄条（过/欠曝）；
* 柱宽 binW×0.9（旧 1/3 错位偏移柱废弃）。

## EV 拖动方向反了（20:40–20:47）

用户反馈 EV 拖动方向反。根因：竖直 ISO/SS 滚轮是**刻度盘手感**（刻度跟手：

两套隐喻相反，体感就是"反的"。

修复：onMove/onUp 两处 `f = dragRefF_ - (x-dragRefPos_)/(0.92*kEvTrackW)`（取负号），
渲染不动（drawRollerH 的 `cx = xMid + (f-curF)*travel`，f=1/EV+ 在右）。
**规则：三条滚轮统一"刻度跟手"——拖动方向 = 刻度移动方向，中心值沿刻度排列方向增减。**

## "从后台返回卡死"根治：引擎生命周期全异步化（22:26–22:38）

### 根因（ANR 堆栈实锤：主线程卡在 NativeActivity.surfaceDestroyed 51s）
glue 主线程在 PAUSE/TERM_WINDOW 里同步 `engine->stop()` → `thread_.join()`；
引擎线程卡在 HAL device close（打盹瞬间 DozeSuspend 挂起，21:06/22:13 两次实锤）
→ join 永不返回 → 主线程冻结 → MIUI Scout ANR。返回前台撞上即"卡死"。

### 修复（三层，全部无阻塞）
1. **引擎生命周期异步化**：`stop()` = 置 stopFlag/wantRun 立即返回；收摊
   （closeSession + cam close + ctl_ reset）由引擎线程在 run 尾部自己完成，
   `running_/stopped_` 在收摊尾部翻转。`requestStart()` 登记意图 + tryStart；
   `tryStart()` 主循环每轮调用（撞上收摊中 → 下轮重试），只在 stopped_ 时
   join（保证已结束、立即返回）并 spawn。析构 detach 不 join。
2. **attach/detach 延迟执行**：异步收摊期间 GL 预览 reader 还被旧会话引用，
   不能立刻销毁 —— INIT 窗口 acquire + pendingWin + wantAttach，主循环在
   engine.stopped() 后 doAttach；TERM/PAUSE 置 wantDetach 同理延迟。
   INIT 抵消挂起的 wantDetach（attach 内部重建 GL）；RESUME 撤销后台 detach。
   主循环 poll 超时：attached=0 / 有挂起操作=100ms / 其余=-1。
3. **每轮运行状态复位**：lastResultMs_/stallRetries_/reconnects_ 是成员、跨
   生命周期残留 —— 重启后看门狗拿旧时间戳误报 stall 51s、且可能开局撞重连
   上限直接退出。run() 开头复位。

### 时序细节（勿踩）
* doAttach 里才 setDataDir/setDisplayRot/attach/requestStart + release pendingWin。
* RESUME 分支简化为 `ui->attached() → requestStart()`（requestStart 幂等，
  running 时 no-op；引擎收摊中则由主循环补启动）。
* 测试干扰源：副屏 subscreencenter 频繁抢 topResumed → PAUSE/RESUME 风暴，
